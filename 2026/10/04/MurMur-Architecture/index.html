MurMur is a Windows voice assistant built with Python and PySide6. This technical walkthrough follows its pipeline from microphone capture to local or cloud speech recognition, text refinement, and guarded insertion into desktop applications. It explains the ONNX and GGUF inference paths, DirectML and Vulkan acceleration, asynchronous session control, Windows UI Automation, clipboard transactions, and local history storage. Based on a pinned v0.4.0 source snapshot, the article also separates implemented behavior from documented validation and the remaining work toward a distributable desktop product.

语音输入看起来只有三个动作：按下快捷键、说话、得到文字。真正把它做成一个能常驻桌面的软件，需要把麦克风采集、识别模型、文字模型、窗口焦点、剪贴板和历史记录协调起来。识别准确只是其中一环：当模型处理期间用户已经切到另一份文档，软件还能不能判断结果应该放在哪里？当润色失败，刚才说的话是否还在？当用户取消后立即开始下一次录音，上一轮迟到的结果会不会覆盖新会话？

MurMur 是我为 Windows 做的语音助手，支持听写、翻译、选中文字编辑，以及用语音提出编辑指令或问题的 Ask Anything。它的技术核心是一条分阶段的输入流水线：先把声音转成原始文字，再按当前模式进行文字处理，最后通过可核验的桌面上下文决定是否上屏。本文基于 2026 年 10 月 4 日的 v0.4.0 源码提交 524c2a8；后续开发中的界面和提示词调整，不属于这个快照。

技术栈与整体架构

MurMur 的桌面客户端使用 Python 3.12+ 和 PySide6，也就是 Qt 的 Python 绑定。主窗口、录音胶囊、结果气泡、预览编辑器与系统托盘都属于 Qt Widgets 路径。桌面应用没有依赖浏览器来承载界面；仓库中的 website/ 是单独的产品官网源码。

层次 主要技术 在 MurMur 中承担的工作
桌面界面 PySide6 / Qt Widgets 主窗口、悬浮胶囊、结果预览、托盘与信号分发
音频采集 sounddevice、NumPy 麦克风 PCM 采集、采样转换和音量计算
本地识别 sherpa-onnx、Silero VAD SenseVoice / Paraformer CPU 推理和语音分段
扩展本地推理 ONNX Runtime DirectML、GGUF、llama.cpp Vulkan、SentencePiece 分拆模型的声学编码、解码和分词
在线识别 DashScope SDK、websocket-client 百炼实时识别与 Alibaba Speech NLS 协议适配
文字处理 httpx、OpenAI 兼容接口 本机 Ollama 或外部服务的整理、翻译、编辑和问答
Windows 集成 pynput、pywin32、comtypes、ctypes 全局快捷键、窗口信息、UI Automation 与原生剪贴板
本地持久化 SQLite、JSON、keyring / Windows Credential Manager 历史、词典、用量、偏好与凭据
工程工具 uv、Hatchling、pytest、PyInstaller 依赖锁定、Python 包构建、测试与桌面打包配置

这里的依赖边界比库名更重要。app.py 中的控制器组织会话；providers.py 提供录音器选择和文字调用；offline.py 与 gguf_asr.py 处理本地识别；windows.py、clipboard.py 管理写入目标；storage.py 保存结果。界面主要分布在 dashboard.py、settings_page.py 和 ui.py。这些边界让“换一个识别引擎”和“改一下结果气泡”可以分别处理。

ASR（Automatic Speech Recognition）与 LLM 的配置彼此独立。ASR 回答“刚才说了什么”，LLM 决定“这段话需要怎样整理、翻译或编辑”。因此，本地识别配云端润色、本地识别配本机 Ollama，或者完全关闭听写润色，都是不同的数据流选择。软件没有把这些选择隐藏在一个模型开关里。依赖版本与模块入口可见固定提交的 pyproject.toml 和 app.py。

从 PCM 音频到原始转写

录音以 16 kHz、单声道、16-bit PCM 进入处理流程。百炼录音路径使用 sounddevice.RawInputStream，每帧 1,600 个采样点，对应约 100 ms。音频回调检查输入格式、计算显示音量，并把音频放入队列；网络发送由另一个线程完成。把采集与网络隔开，可以避免一次慢发送直接拖住实时音频回调。

缓冲区同时有容量限制。应用侧队列和百炼 SDK 的内部发送队列都限制为 50 项；队列溢出会结束录音并提示错误，而不是一直积压音频。源码固定 dashscope==1.27.7，因为内部队列适配使用了 SDK 的私有字段，并在运行时检查版本与字段形态。这是一个明确的维护代价：升级 SDK 时，需要重新验证这段适配，不能只改依赖版本。

胶囊的录音动画来自真实 PCM 的 RMS 音量。audio_levels.py 将幅度转换为 dBFS，再用固定范围映射到 0–1。这个值用于显示声音强弱；它没有被当成识别置信度，也没有承担 VAD 的职责。把“音量表”和“是否在讲话”分开，能避免界面表现和识别决策混用一个指标。

本地识别则在停止录音后执行。PCM 转为归一化浮点采样，Silero VAD 按停顿划分语音段，再逐段送入所选模型。默认 VAD 最大语音段约 20 秒，边界前后保留少量上下文，减少裁掉较轻音节的风险；整次本地录音限制为 10 分钟。录音时胶囊持续变化，并不表示离线模型在实时逐字解码。 原始转写阶段与录音阶段在实现上是分开的。对应实现见 providers.py、offline.py 和 audio_levels.py。

四种本地模型，以及为什么要隔离推理进程

当前源码支持四种本地识别模型，但它们并没有共用一种权重格式与推理路径。

模型 CPU 路径 GPU 路径 实现上的区别
SenseVoice Small INT8 ONNX，经 sherpa-onnx 分拆 FP16 ONNX，经 DirectML CPU / GPU 使用不同模型目录和文件结构
Paraformer INT8 ONNX，经 sherpa-onnx 当前未接入 当前安装没有独立标点模型，可交给后续文字处理
Fun-ASR-Nano ONNX 编码器与 Q5_K GGUF 解码器 DirectML 编码器与 Vulkan 解码器 声学编码和生成式解码由不同运行库处理
Qwen3-ASR 1.7B 分拆 ONNX 与量化 GGUF 解码器 DirectML 编码器与 Vulkan 解码器 需要匹配的编码器文件、GGUF 权重及运行库

这套适配使用指定转换模型。它不是一个能加载任意 PyTorch 或 GGUF 文件的通用推理器。models.py 保存模型描述、必需文件和下载校验信息；安装阶段检查固定大小与 SHA256，运行时还会检查目录与引擎是否匹配。下载由用户主动触发，识别过程本身不下载模型。

一个容易忽略的 Windows 问题是动态库冲突。sherpa-onnx 的运行环境与 ONNX Runtime DirectML 可能带有同名 DLL。如果把不同运行库都直接加载到桌面进程，模型切换会变成进程级的依赖管理问题。MurMur 在 gguf_asr.py 中使用 multiprocessing 的 spawn 子进程加载扩展引擎，通过本地 Pipe 传递 PCM 与普通结果消息，使这些原生依赖与主进程隔离。Silero VAD 仍保留在 CPU 路径。

本地识别器按引擎、加速方式、文件状态、语言和线程数缓存；推理使用单个解码槽，避免服务测试和录音处理同时切换正在使用的模型。独立推理任务取消时可终止工作进程，让下一次加载从干净状态开始。这比单纯隐藏一个窗口复杂，但能处理“模型还在原生库里计算，用户已经取消”的情况。

这里的 GPU 含义是 DirectML 与 Vulkan，不是 CUDA。GPU 不可用或模型缺失时会显示错误，用户可以手动切回 CPU；音频不会自动转发云端。这也意味着模型可用性与显卡收益需要在具体机器上验证，不能根据 GPU 开关推断速度。实现与来源分别见 gguf_asr.py、native_runtime.py 和 第三方说明。其中部分 ONNX/GGUF 推理辅助代码改编自 CapsWriter-Offline，并保留了来源与许可证。

文字模型的职责：听写数据与编辑指令分开

文字处理使用 httpx 调用兼容的 /chat/completions 接口。通用请求包含模型名、messages 和低温度参数；本机 Ollama 与外部服务复用这个传输层。Auto 模式只发现已存在的本地模型，不负责安装模型，也不在本地服务失败后改用云端。对明确配置或探测确认的 Ollama，程序会附加关闭思考的参数；未知服务保持通用请求格式。

普通听写有一项关键约束：口述中的命令仍然是需要转写的内容。 例如说“请把这句话翻译成英文”，如果当前是听写模式，结果应该保留这句话，而不是直接执行翻译。因此源码把转写放进 dictation 字段，配合系统规则和少量示例，要求模型保留原语言、英文术语与原有引号，只做有限清理。

这是一轮请求的结构化路由，当前没有联网检索、连续对话或外部工具执行。普通听写与 Ask 的区别，也说明提示词不能只用一套“让文字更好”的笼统要求：前者处理原始数据，后者处理编辑指令。当前快照的听写仍以最小改动为主；把长段口语重构为层次清晰的书面稿，需要额外定义编辑尺度并验证，不应混同为已经完成的能力。相关源码见 providers.py、local_llm.py 和 assistant.py。

异步会话：处理取消、迟到结果和阶段进度

模型加载、网络请求与转写都可能较慢。MurMur 用后台 Python 线程执行这些工作，经 Qt 的 Signal 把消息送回控制器，而界面更新留在 Qt 事件循环中。每次操作对应一个 Session，携带唯一 ID、配置的深拷贝、取消事件、原始目标、转写文本和处理阶段。配置快照让一次录音的行为不会随着中途改设置而漂移。

胶囊进度同样来自会话的实际阶段。开启整理的听写是 Transcribe → Polish，翻译是 Transcribe → Translate，百分比按已完成步骤推进，两阶段任务通常表现为 0%、50%、100%。这是阶段完成比例：它不代表模型内部已经计算了多少 token，也不是耗时预测。识别结束后，界面可以明确告诉用户正在等待文字处理，而不用凭定时器假装进度在增长。会话与进度实现见 app.py。

Windows 上屏：重新确认目标，再处理剪贴板

得到最终文本以后，最棘手的一步是把它写到正确位置。MurMur 在开始时记录前台窗口、焦点控件和进程信息，通过 Win32 与 UI Automation 判断目标是否可编辑；处理期间继续观察焦点和物理输入。对于 Ask 的替换与插入，还会保存选区或光标的上下文书签，在写入前确认范围与内容仍然有效。

UI Automation 的 COM 文本范围保留在专用 MTA 线程中，其他线程使用书签令牌来引用它们。选区校验涉及范围端点和文字；光标上下文还使用邻近文字的局部指纹，检查生成期间是否已经有变化。不能确认目标、用户中途输入、密码字段或监听不可用时，结果回到预览，由用户复制使用。

传统选区编辑也先预览，点击 Replace 后再次校验；Ask 的语音编辑只有动作与上下文匹配并通过检查时才自动替换。即使应用显示“Paste sent”，它也只说明粘贴已经发出，不等同于通用地证明每个第三方编辑器都完成了写入。跨应用行为仍需要实际验收。

剪贴板还有第二种竞态：软件暂存了旧内容，处理中用户又复制了新内容。如果结束时无条件恢复旧快照，就会抹掉这次复制。MurMur 的原生剪贴板事务比较版本、所有者和内容，只在条件仍匹配时恢复，且以可保存的纯文本格式为边界。复杂富文本无法可靠保全时回退预览。

需要区分两种行为：真实听写与翻译成功后，最终结果默认会写入剪贴板；选区捕获、替换以及粘贴事务则负责保护其临时读写过程，不覆盖事务期间产生的新内容。“保护剪贴板”不意味着听写永远不改变剪贴板。Windows 集成的具体实现见 windows.py 和 clipboard.py。

历史、词典与数据边界

历史数据库使用 SQLite，分别保存 raw 和 final。前者保留原始 ASR 结果，后者保存整理或翻译后的结果；Ask 还保存本次选区来源 context。记录同时包含模式、录音时长、处理延迟、错误和可选音频位置。两份文本让问题可以被拆开诊断：是识别把术语听错了，还是文字模型删掉了细节？只保留最终结果，会把这两类问题混在一起。

识别或模型调用失败时，已有原文仍留在结果气泡供复制或编辑，不把部分转写自动上屏。历史写入失败也不会让当前结果消失，界面会提示未保存。删除流程先提交数据库删除，再清理关联录音；被占用的音频会进入持久待删队列，在后续启动时重试。JSON/CSV 导出则先完成新文件写入，再替换目标文件。

个人词典以 SQLite 为准，旧设置中的热词只初始化导入一次。它既能为支持上下文的在线识别提供词汇线索，也配合文字处理前的字面替换规则；这些不同机制不能等同于所有本地模型都支持原生热词解码。词汇建议来自本地真实历史，演示样本排除在分析之外，并由用户逐条确认。

普通偏好保存为 JSON，服务密钥通过 keyring 的 Windows 凭据后端保存。默认不保存录音，历史默认保留 90 天。当前源码把应用数据、模型和运行库分开放置，但默认根目录仍固定于开发机器使用的本地路径；虽然 --data-dir 可以覆盖应用数据目录，安装版仍需要进一步设计可移植的模型与运行库路径。

“本地”需要沿整条链路判断。离线 ASR 只保证识别音频留在本机；若后续选择云端润色，文字依然会发送到该服务。本机回环地址的 Ollama 与关闭润色是本地听写路径，而远程、局域网模型服务及当前 Ask 外部接口都有各自的数据出口。用量统计另存服务返回的 token 与计价元数据；缺失用量不会按文本长度猜测，估算费用也不是实际账单。存储及数据说明见 storage.py 和 README。

工程状态与后续工作

复现依赖使用 uv.lock，基本开发入口如下。首次真实使用还需安装所选语音模型，并配置或关闭文字处理；当前固定默认存储路径也应结合自己的机器检查。

仓库的验证记录报告：v0.3.1 应用快照通过 927 项回归测试；v0.4.0 复用同一应用实现，并另外通过 37 项版本、存储、会话与配置相关检查。这些数字是项目已记录的本地验证证据，本文没有重新运行这组测试。 模拟测试与离屏界面检查能覆盖状态流转、错误恢复、数据保存和部分界面行为；实际麦克风、快捷键、AltGr/输入法、混合 DPI 多屏，以及不同应用的完整听写到上屏仍需要现场验证。

当前 v0.4.0 是源码阶段版本，产品官网已发布，但 Windows 安装包尚未交付。构建脚本保留组织安全阻挡，PyInstaller 配置的存在不代表已有可分发安装器。解除阻挡后，还要完成安装器、升级和卸载流程，以及原生依赖和模型许可证的分发检查。应用源码采用 MIT，模型权重与第三方依赖各有自己的许可，不能直接沿用应用源码的许可结论。相关边界见 v0.4.0 发布记录 和 验证记录。

对我来说，MurMur 最有价值的工程实践，是把每个结果放回它所属的上下文：原始转写和文字加工分别保留，异步回调归属于具体会话，模型给出的编辑动作还要经过桌面目标校验。本地模型解决了语音在哪里处理，窗口与数据机制则决定这个结果能否可靠地进入日常工作。接下来值得继续完善的，是长段口语的书面化质量、跨应用的真实验收，以及把当前开发环境整理成可安装、可更新的桌面产品。
