Read in

MurMur turns a hotkey and a microphone into a small Windows voice assistant. Under the floating capsule are Python, Qt, local speech models, optional cloud APIs, and quite a bit of code devoted to getting text into the right window. Here is a tour of the interesting bits: ONNX and GGUF inference, GPU workers, prompts that distinguish dictation from commands, and clipboard races. It follows the v0.4.0 source snapshot, including the rough edges that still need work.

The fun part of a voice tool is watching your words appear on screen. The awkward part is realizing that, while the model was thinking, you switched windows, moved the cursor, copied a link, and started another recording. Now the app has a perfectly good sentence and several opportunities to put it somewhere ridiculous.

MurMur is my Windows voice assistant for dictation, translation, selected-text editing, and spoken requests through Ask Anything. Its visible footprint is a floating capsule; the main window holds history, a dictionary, settings, and activity stats. Press a key, talk, finish the recording, and get a draft you can use.

This post opens the box. The code we’re looking at is v0.4.0, commit 524c2a8, from October 4, 2026. The project is still moving, so this is a snapshot of what that code actually does.

The stack: Python, Qt, and a pipeline you can take apart

The desktop app uses Python 3.12+ and PySide6, with Qt Widgets for the dashboard, capsule, result bubble, editor, and tray. The product website lives separately in website/. The basic route is easy to sketch:

Speech recognition and text processing have separate settings. One figures out what you said; the other cleans it up, translates it, or handles an editing request. You can run local recognition with Ollama, pair it with an external text model, or turn dictation refinement off.

The code follows that route. app.py runs sessions; providers.py selects recorders and calls text models; offline.py and gguf_asr.py handle local recognition. windows.py and clipboard.py do desktop delivery, while storage.py keeps the evidence. UI code lives mostly in dashboard.py, settings_page.py, and ui.py. You can work on a speech backend without rebuilding the result bubble. Start with the dependency list and the controller.

Audio: keep the microphone callback boring

Audio enters as 16 kHz, mono, 16-bit PCM. In the DashScope path, sounddevice.RawInputStream supplies 1,600 samples per frame—about 100 ms. The callback checks the frame, computes a display level, and drops bytes into a queue. A separate thread sends them to the service. Network delays don’t belong inside a microphone callback.

Both the app’s audio queue and the adapted DashScope sending queue have a 50-item limit. If a queue fills up, recording stops with an error instead of hoarding audio indefinitely. The slightly spicy detail: the adapter touches a private SDK field. That is why dashscope==1.27.7 is pinned, with a runtime compatibility check. An SDK upgrade means revisiting that adapter.

The waveform comes from actual PCM RMS levels, converted to dBFS and mapped to a fixed display range. It shows volume; it doesn’t measure recognition confidence or decide where speech ends. Offline recognition starts after recording stops: NumPy converts samples, Silero VAD splits around pauses, and the selected model decodes segments. VAD targets segments up to roughly 20 seconds, with padding around boundaries; a recording is capped at 10 minutes. A lively capsule doesn’t mean the local model is decoding every word live. See providers.py, offline.py, and audio_levels.py.

Four speech models, and the DLL rabbit hole

The local model menu hides several different inference setups:

Model CPU route GPU route
SenseVoice Small INT8 ONNX through sherpa-onnx Split FP16 ONNX through DirectML
Paraformer INT8 ONNX through sherpa-onnx Not connected in this snapshot
Fun-ASR-Nano ONNX encoder + Q5_K GGUF decoder DirectML encoder + Vulkan decoder
Qwen3-ASR 1.7B Split ONNX + quantized GGUF decoder DirectML encoder + Vulkan decoder

These are specific converted models with expected file layouts. Dropping an arbitrary GGUF into the folder won’t make it work. SenseVoice CPU and GPU use different files; Paraformer currently has no separate punctuation model, so text refinement can supply punctuation afterward.

Then comes Windows DLL loading. The sherpa environment and ONNX Runtime DirectML can ship different libraries with the same name. Loading them all into the UI process is an excellent way to make model switching more exciting than intended.

MurMur puts the extended engines in a spawned worker process. PCM and result messages travel through a local Pipe; the worker owns its native libraries. VAD stays on the CPU. The recognizer cache tracks the engine, acceleration, files, language, and thread settings, while a single decode slot prevents a model switch from closing a worker during inference. Cancelling an isolated native job can terminate its worker so the next load starts cleanly.

GPU here means DirectML and Vulkan, with no claimed CUDA path or universal speedup. Missing files or unavailable acceleration produce a local error; they don’t silently upload a recording to the cloud. Downloads are explicit and checked against pinned sizes and SHA256 hashes. Some inference helpers are adapted from CapsWriter-Offline, with attribution and licenses retained. See gguf_asr.py, native_runtime.py, and third-party notes.

“Translate this” can be a sentence or a command

Text processing uses httpx to call /chat/completions. Ollama and external compatible services share that transport. Local Auto discovers existing models; it doesn’t install one or fall back to cloud. Recognized Ollama servers get a parameter to disable thinking; unknown servers keep the generic request format.

Now imagine dictating “Please translate this sentence into Chinese.” In dictation mode, those words should appear in your document. The model shouldn’t become a translator just because the sentence sounds like a request. MurMur wraps dictation as data, adds language-preservation rules, and supplies editing examples. Ask Anything gives the spoken request a different role. It sends instruction and selected_text to its own external HTTPS profile and asks for a tiny JSON response:

Allowed actions are replace, insert, and answer. Editing a selection can replace it; drafting can insert text; questions show an answer. Summarizing defaults to an answer unless you explicitly request replacement. The parser checks exact fields, a valid action, and nonempty text; replacement requires a selection. Desktop checks still happen afterward.

This is one request with a small routing contract. No browsing, ongoing conversation, or external tool execution is implemented here. Ordinary dictation also remains conservative: filler cleanup is implemented, while turning a rambling monologue into a well-structured document still needs more prompt work and examples. That split lives in providers.py, local_llm.py, and assistant.py.

Cancel means the old result doesn’t get a comeback

Python threads handle recording startup, recognition, model loading, and network work. Qt signals bring messages back to the controller, keeping widget updates in the UI event loop. Each operation gets a Session: an ID, a deep copy of settings, a cancellation event, the original target, raw text, and a phase. Changing a preference halfway through a recording doesn’t change that recording’s rules.

The ID handles a classic asynchronous nuisance: cancel A, start B, then receive A’s late result. The controller’s first check is wonderfully unglamorous:

Old callbacks don’t get to announce that a new session is finished. Cancellation reaches resource cleanup and requests, and semaphores bound concurrent requests while old ones unwind. Hiding the capsule alone wouldn’t do that.

Progress follows session state, too. Dictation with refinement runs Transcribe → Polish; translation runs Transcribe → Translate. A two-stage job moves through 0%, 50%, and 100% as stages finish. The app knows which step completed, so that’s what it displays. It has no model-internal percentage or ETA to report. See app.py.

Pasting is where the desktop gets involved

By the time a result arrives, the cursor may have moved. MurMur captures window, focused-control, and process information, then watches focus and physical input. Win32 and UI Automation help decide whether the target is still editable. For Ask edits, selection or caret bookmarks recheck the text range before writing.

COM text ranges stay on a dedicated MTA thread; other threads carry bookmark tokens. Selection checks compare endpoints and text. Caret checks use a local fingerprint of surrounding text. A changed target, password field, uncertain control, or unavailable input monitor sends the result to preview. Regular selection editing starts in preview and checks again when you click Replace. Ask can write automatically when its action and captured context match and the checks pass. “Paste sent” means dispatched; real-app testing still matters.

The clipboard has its own race. The app temporarily saves its contents, then you copy something else. Blindly restoring the snapshot would erase your new copy. Native transactions compare revisions, ownership, and content before restoring supported plain-text formats. Rich content that can’t be safely preserved falls back to preview.

Successful real dictation and translation do copy the final result by default. Transaction machinery protects temporary capture/paste work and newer clipboard changes; it doesn’t promise an untouched clipboard after dictation. This part lives in windows.py and clipboard.py.

Keep the raw transcript—it makes debugging less mysterious

SQLite stores raw and final, plus mode, duration, latency, errors, and an optional audio path. Ask also keeps selected-text context. You can separate “the recognizer misheard the word” from “the text model edited it away.” Keeping only the pretty final paragraph loses that clue.

A failed model call leaves recovered text available. A failed history write doesn’t throw away the current result. Deletion commits the database change before removing recordings; locked audio files enter a persistent retry queue. Exports finish a new file before replacing the old one. The SQLite dictionary supports individually confirmed suggestions from real history and literal replacement rules. Some online models accept vocabulary context; that doesn’t make every offline engine a hotword-aware decoder. Demo samples stay out of vocabulary analysis.

Settings are JSON; secrets use Windows Credential Manager. Audio saving is off by default, and history defaults to 90 days. Token counts come from service responses, with estimated costs kept separate from actual billing.

One development-machine wrinkle: this snapshot hardcodes its default project root. --data-dir overrides app data, but portable model/runtime locations need work. Also, local ASR says where audio is recognized. Cloud refinement still sends text out; loopback Ollama keeps that step on the machine, while LAN servers, remote servers, and the current Ask profile have their own destinations. See storage.py and the README.

录音回调，越无聊越好

输入是 16 kHz、单声道、16-bit PCM。百炼路径使用 sounddevice.RawInputStream，每帧 1,600 个采样点，也就是约 100 ms。回调检查音频、计算显示音量，然后把字节塞进队列；另一个线程负责发送。网络卡一下，不应该拖住麦克风回调。

应用侧和适配后的百炼发送队列都限为 50 项。队列填满，就结束录音并提示错误，避免无限囤积音频。这里有个需要留心的细节：适配器碰了 SDK 的私有字段，所以固定 dashscope==1.27.7，运行时检查兼容性。以后升级 SDK，这块得重新看。

胶囊波形来自真实 PCM 的 RMS 音量，转成 dBFS 后映射到固定显示范围。它显示声音强弱，不承担识别置信度或判断语音起止的工作。离线模型在录音结束后开始识别：NumPy 转换采样，Silero VAD 按停顿切段，再交给模型。VAD 单段最多约 20 秒，边界前后留一点余量，整次录音最多 10 分钟。胶囊跳得欢，不等于本地模型正在实时逐字解码。细节在 providers.py、offline.py 和 audio_levels.py。

四个模型，以及 DLL 的坑

本地模型下拉菜单背后，其实是几套不同的推理方式：

模型 CPU 路径 GPU 路径
SenseVoice Small sherpa-onnx 跑 INT8 ONNX DirectML 跑分拆 FP16 ONNX
Paraformer sherpa-onnx 跑 INT8 ONNX 当前快照未接入
Fun-ASR-Nano ONNX 编码器 + Q5_K GGUF 解码器 DirectML 编码器 + Vulkan 解码器
Qwen3-ASR 1.7B 分拆 ONNX + 量化 GGUF 解码器 DirectML 编码器 + Vulkan 解码器

这里用的是指定转换模型，要匹配文件结构。随手丢进一个 GGUF，并不会自动识别。SenseVoice 的 CPU/GPU 使用不同文件；Paraformer 没有独立标点模型，标点可以交给后面的文字整理。

接着碰到 Windows 动态库问题：sherpa 环境和 ONNX Runtime DirectML 可能带着不同版本的同名 DLL。全塞进界面进程，模型切换就容易变得比预期刺激得多。

MurMur 把扩展引擎放进 spawn 子进程，通过本地 Pipe 传 PCM 和结果，让子进程自己管理原生库。VAD 继续走 CPU。识别器按引擎、加速方式、文件、语言和线程设置缓存；单个解码槽避免切模型时关掉正在计算的工作进程。取消独立原生任务时，可以终止它的子进程，让下一次加载重新开始。

GPU 指的是 DirectML 和 Vulkan，没有宣称 CUDA 路径，也不能看到 GPU 选项就假定一定更快。缺文件或显卡不支持时，会报本地错误，不会悄悄把录音传到云端。下载要主动触发，安装时检查固定大小与 SHA256。部分推理辅助代码改编自 CapsWriter-Offline，并保留来源与许可。对应 gguf_asr.py、native_runtime.py 和 第三方说明。

“翻译这句话”，到底是一句话还是一个命令？

文字处理用 httpx 调 /chat/completions，Ollama 与外部兼容服务复用传输层。本地 Auto 只找已安装的模型，不安装模型，也不在失败时改用云端。确认是 Ollama 时会加关闭思考的参数，未知服务保留通用格式。

动作只有 replace、insert、answer。改选区可以替换，起草可以插入，提问则显示答案。总结默认也只是回答，除非明确要求替换原文。解析器检查精确字段、有效动作与非空正文，没有选区不能替换，之后还要过桌面检查。

取消了，就别让旧结果诈尸

录音启动、识别、模型加载和网络请求由后台 Python 线程处理，通过 Qt 信号交回控制器，让控件更新留在界面事件循环。每次操作有一个 Session，带 ID、设置深拷贝、取消事件、原始目标、原文和处理阶段。中途改偏好，不会改变这次录音的规则。

旧回调不能把新会话宣布为“完成”。取消还传给资源清理与模型请求，信号量限制尚未收尾的请求数量。光把胶囊藏起来，没有真正取消这些工作。

进度也使用会话状态：听写整理是 Transcribe → Polish，翻译是 Transcribe → Translate；两阶段任务按完成步骤显示 0%、50%、100%。知道哪一步做完，就显示哪一步。模型内部进度和预计剩余时间，接口没有给出来。实现见 app.py。

粘贴这一步，才轮到桌面出场

结果回来时，光标可能早就挪了。MurMur 记录窗口、焦点控件和进程信息，观察焦点与物理输入，再通过 Win32 和 UI Automation 判断目标是否仍可编辑。Ask 保存选区或光标书签，写入前核对文字范围。

COM 范围留在专用 MTA 线程，其他线程拿书签令牌引用。选区检查端点与文字，光标检查邻近文字的局部指纹。目标改变、密码框、无法确认的控件或监听不可用时，结果留在预览。传统选区编辑先预览，点击 Replace 再查；Ask 的动作与上下文匹配、检查通过时可以自动写入。“Paste sent”只表示已发出粘贴，真实应用还得测试。

剪贴板也有竞态。软件临时保存了旧内容，这时你复制了别的东西。无条件恢复快照，会把新复制的内容抹掉。原生事务比较版本、所有者和内容，再决定能否恢复支持的纯文本格式；复杂富文本无法可靠保全，就回退预览。

真实听写与翻译成功后，默认会把最终结果写入剪贴板。事务保护临时捕获、粘贴过程与期间产生的新内容，并不承诺听写后剪贴板完全不变。实现见 windows.py 和 clipboard.py。

原始转写别扔，调试时真的好用

SQLite 分别保存 raw、final，还有模式、时长、延迟、错误与可选音频路径，Ask 另外保存选中文字 context。看到怪话，可以分清是识别器听错了，还是文字模型改没了。只存最后漂亮的段落，会丢掉这个线索。

模型失败，已有原文还能用；历史写入失败，也不会丢掉当前结果。删除先提交数据库，再清理录音，被占用的文件进入持久重试队列。导出先写完整新文件，再替换旧文件。SQLite 词典支持真实历史建议、逐条确认与字面替换。部分在线模型支持词汇上下文，但不等于每个离线引擎都支持热词解码。Demo 样本不参与词汇分析。

偏好是 JSON，密钥交给 Windows Credential Manager。录音默认不保存，历史默认保留 90 天。Token 来自服务返回值，估算费用与实际账单分开。

一个开发阶段的小尾巴：默认项目根目录仍写死在本地路径里。--data-dir 能覆盖应用数据，但可移植的模型、运行库位置还要做。另外，本地 ASR 只说明音频在哪里识别；云端整理仍发出文字，回环 Ollama 留在本机，局域网、远程服务与当前 Ask 则各有数据出口。对应 storage.py 和 README。

发布记录里，v0.3.1 应用快照有 927 项回归测试通过，v0.4.0 沿用该实现，并额外通过 37 项版本、存储、会话与配置检查。这是项目记录，本文没有重跑。模拟与离屏检查有帮助，但真实麦克风、物理快捷键、AltGr/输入法、混合 DPI 多屏和跨应用上屏，仍需现场折腾。
